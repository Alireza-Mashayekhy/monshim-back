# آیا این ساختار در آینده مشکل پیدا می‌کند؟

**تاریخ:** ۲۰۲۶-۱۱-۰۸ · **شاخه:** `arena/bd03e7a3-monshim`

> این سند نتیجهٔ **آزمایش** است، نه نظر. هر ادعا با یک اجرا پشتیبانی شده.
> هر جا آزمایش نکردم، صریح نوشته‌ام.

---

## خلاصهٔ یک‌خطی

**ساختار برای آیندهٔ نزدیک و متوسط امن است.** یک باگ واقعی داشت که پیدا و رفع شد.
سه ریسک باقی‌مانده «قابل مدیریت» هستند و یکی از آن‌ها (بازتولید بردارها)
راه‌حل مستند دارد. **هیچ‌کدام از این‌ها مانع merge نیستند.**

---

## ۱. باگ واقعی که پیدا شد: مولد بردار متن **اجرا نمی‌شد**

این جدی‌ترین یافته است. اگر کسی فردا الگوریتم را آگاهانه عوض می‌کرد و طبق
دستور مستندشده سعی می‌کرد بردارها را بازتولید کند:

```bash
$ node shared/generate-text-vectors.mjs
Error [ERR_MODULE_NOT_FOUND]: Cannot find module
  '.../back/src/common/utils/digits.util'
  imported from '.../national-code.util.ts'
```

**علت:** `national-code.util.ts` خط ۲۸ این را دارد:

```ts
import { toEnglishDigits } from './digits.util';   // بدون پسوند
```

Node به دنبال فایل دقیق `./digits.util` می‌گردد، پیدا نمی‌کند
(فایل واقعی `digits.util.ts` است). TypeScript و tumbleweed این را حل می‌کنند، Node نه.

**نتیجه:** بردارها قابل بازتولید نبودند. یعنی اگر منطق عوض می‌شد، تنها راه
به‌روزرسانی قفل — که همان چیزی است که از divergence جلوگیری می‌کند — **بسته بود**.

**رفع:** `shared/register-ts-resolver.mjs` + `shared/ts-extension-resolver.mjs`
(هوک استاندارد `node:module`، بدون هیچ وابستگی جدید). فقط در زمان اجرای
مولد بارگذاری می‌شود؛ **اثر صفر** روی بیلد، Production یا باندل Next.

**تأیید:** مولد حالا کار می‌کند و خروجی‌اش **بایت‌به‌بایت** با فایل commit‌شده یکسان است:

```
$ node --import ./shared/register-ts-resolver.mjs shared/generate-text-vectors.mjs
✓ 20 digit + 43 national-code + 20 persian بردار نوشته شد
$ git diff --stat shared/text-vectors.json
(خالی ← قطعی و تکرارپذیر)
```

### و یک شکنندگی که پیش‌دستی رفع شد

`generate-pricing-vectors.mjs` **امروز** کار می‌کرد، ولی فقط چون
`deposit-amount.ts` هیچ import بدون پسوندی ندارد. اگر فردا کسی یکی اضافه می‌کرد،
**بی‌صدا** می‌شکست. حالا هر دو مولد با همان `--import` اجرا می‌شوند و
دستور درست در بالای هر دو فایل نوشته شده.

این مهم‌ترین سؤال است. «قفل همسانی» تمام توجیه این ساختار است.

### آزمایش ۴ (مهم‌ترین) — تغییر آگاهانه + بازتولید بردارها

این سناریوی واقعی آینده است: «منطق را عوض کردم، بردارها را بازتولید کردم.»
اگر بردارها را از کد **جدید** بسازیم و فرانت **کهنه** بماند، چه می‌شود؟

```

۲. node --import ./register-ts-resolver.mjs shared/generate-pricing-vectors.mjs

۳. فرانت تست:
   # pass 3 / # fail 2            ← فرانت کهنه گرفته شد ✅
```

✅ **گرفته شد.** یعنی حتی اگر کسی بردارها را «درست» بازتولید کند،
فرانت کهنه بلافاصله شکست می‌خورد. **این دقیقاً همان تضمینی است که دنبالش بودیم.**

## ۳. ریسک‌های باقی‌ماندهٔ «آینده» — با شدت واقعی

### 🟡 ریسک ۱: مسیر `shared/` به ساختار پوشه وابسته است

| طرف | نحوهٔ حل مسیر |
|---|---|
| بک‌اند | `path.resolve(__dirname, '../../..', 'shared', ...)` |
| فرانت | `path.resolve(import.meta.dirname, '..', '..', 'shared', ...)` |

**اگر در آینده:**
- تست بک‌اند را از `src/payment/` به عمق دیگری جابه‌جا کنید → `../../..` غلط می‌شود
- پروژه را مونوریپو کنید → `shared/` جای دیگری می‌رود
- `shared/` را rename کنید

...تست با `ENOENT` می‌شکند (نه با پیام واضح).

**شدت: متوسط.** چرا که:
- **بی‌صدا شکست نمی‌خورد** — تست بلافاصله قرمز می‌شود، فقط پیامش گویا نیست
- فقط **تست‌ها** را می‌شکند، نه بیلد یا Production (بند ۴ را ببینید)

**پیشنهاد (اعمال نشده — نیازمند تأیید):** یک `shared/README.md` کوتاه یا
یک تست که وجود فایل را با پیام واضح چک کند. هزینه: ۵ دقیقه.

### 🟡 ریسک ۲: کد **تولید** متکی به `shared/` نیست — که هم خوب است هم بد

```
$ grep -rn "shared/" back/src --include=*.ts | grep -v spec.ts
(خالی)
```

**خوب:** بیلد و دیپلوی هیچ وابستگی‌ای به `shared/` ندارند. اگر روزی `shared/`
گم شود، Production سالم می‌ماند.

**بد:** یعنی `shared/` **فقط در تست‌ها** محافظ است. اگر کسی تست‌ها را اجرا
نکند (مثلاً بدون CI — که الان وضعیت واقعی ماست)، قفل عملاً بی‌اثر است.

**شدت: بالا — ولی علتش CI است، نه ساختار.** این دقیقاً همان شکافی است که در
`09-CI-CD.md` مستند شد: تا وقتی `.github/workflows/ci.yml` کامیت نشود،
هیچ‌کس تست‌ها را اجباری اجرا نمی‌کند.

### 🟢 ریسک ۳: حجم فایل بردارها

`shared/pricing-vectors.json` = ۱۶٬۳۸۰ خط (~۵۰۰ کیلوبایت) در هر diff و clone.

**شدت: پایین.** یک‌بار در کل تاریخ پروژه عوض می‌شود (فقط وقتی الگوریتم عوض شود).
git فشرده‌اش می‌کند. تأثیری روی بیلد یا اجرا ندارد.

### 🟢 ریسک ۴: Docker و `shared/` — **تست شد، مشکلی نیست**

نگرانی منطقی: `shared/` بیرون از پوشهٔ `back/` است، و `docker-compose.yml`
context را `.` (یعنی `back/`) می‌گذارد. پس `shared/` در ایمیج نیست.

**آیا بیلد می‌شکند؟** آزمایش کردم — یک کپی از `back/` ساختم که `shared/` نداشت
(دقیقاً مثل build context واقعی) و همان مراحل Dockerfile را اجرا کردم:

```
$ pnpm install --frozen-lockfile   →  exit 0
$ pnpm run build                    →  exit 0
$ ls dist/src/main.js              →  وجود دارد ✅
```

**تأیید شد: بیلد Docker سالم است.** چون فقط spec‌ها به `shared/` نیاز دارند و
Dockerfile تست اجرا نمی‌کند.

⚠️ **ولی:** اگر روزی کسی تست را به Dockerfile اضافه کند، شکست می‌خورد.
این را در `Dockerfile` یادداشت کردم.

### 🟢 ریسک ۵: دو نسخه pnpm

```
back  → pnpm 8.15.4 (lockfileVersion 6)
front → pnpm 9       (lockfileVersion 9)
```

**شدت: پایین برای آیندهٔ نزدیک** — هر دو در CI و pre-commit صریح پین شده‌اند.
**ولی** روزی که بخواهید مونوریپو کنید، این همان بلاکری است که در فاز ۴
اندازه‌گیری شد: `pnpm@8.15.4` نمی‌تواند لاک‌فایل v9 را بخواند.

## ۴. «آیا ساختار جلوی رشد را می‌گیرد؟»

| سناریوی آینده | مشکل می‌شود؟ |
|---|---|
| افزودن endpoint جدید | ✅ نه — الگوی موجود، صفر اصطکاک |
| افزودن صفحهٔ جدید فرانت | ✅ نه |
| تغییر منطق قیمت‌گذاری | ⚠️ **عمداً** باید هر دو طرف + بازتولید بردارها |
| افزودن وابستگی | ✅ نه (ولی CI/Dependabot را فعال کنید) |
| ارتقای major یک پکیج | ✅ نه — Dependabot عمداً major را ignore می‌کند |
| مونوریپو کردن | ❌ همان بلاکرهای فاز ۴ (۵۲ نسخه + pnpm 8 vs 9) |
| آپدیت Next.js | ⚠️ **ریسک واقعی** — یک صفحهٔ از قبل خراب در مسیر webpack |
| افزودن تیم / نفر دوم | ❌ **بدون CI و branch protection، ریسک بالا** |

### دو مورد که باید بدانید

**۱. `next build --webpack` از قبل خراب است.** کدبیس یک page export نامعتبر
دارد (`SLOT_INTERVAL_OPTIONS` در `app/(dashboard)/dashboard/work-hours/page.tsx`).
Turbopack آن را نادیده می‌گیرد. اگر روزی Next مجبورتان کند به webpack برگردید،
**بیلد می‌شکند**. این از قبل وجود داشته و به این تغییرات ربطی ندارد، ولی
نگفته نماند.

**۲. بدون CI، ساختار «امن» نیست — فقط «امن‌تر» است.** قفل بردارها فقط وقتی
ارزش دارد که هر push اجرا شود. الان نمی‌شود.

## ۵. جمع‌بندی صادقانه

### آیا در آینده مشکل پیدا می‌کند؟

**برای ۶ تا ۱۲ ماه آینده، با یک توسعه‌دهنده: نه.**

**شرطش این است:**

1. ✅ **`.github/workflows/ci.yml` را کامیت کنید** — بدون این، قفل بردارها
   تشریفاتی است. (۳۰ ثانیه، و من مجوزش را ندارم)
2. ✅ **branch protection روی `main`** — هیچ کدنویسی لازم ندارد
3. ✅ کارهای `pre-commit` را نصب کنید: `git config core.hooksPath .githooks`

**اگر این سه کار را نکنید:** ساختار **بدتر** از قبل نیست، ولی تضمینی که
ساخته‌ایم **فعال نمی‌شود**. مثل قفل خریده و نصب نکرده.

### آیا این ساختار جلوی رشد را می‌گیرد؟

**نه.** تنها چیزی که عمداً «سخت» شده، تغییر منطق پول است — و این **ویژگی**
است، نه باگ. در پروژه‌ای که پول جابه‌جا می‌شود، کندی عمدی در تغییر منطق پول
ارزشمند است.

### چیزی که هنوز نمی‌دانم

- رفتار روی **MySQL/Redis واقعی** (در این محیط دیتابیس نیست)
- `docker build` واقعی (Docker نیست)
- عملکرد Nginx/PM2/SSL روی سرور شما

این‌ها را نمی‌توانم «امن» بنویسم — فقط «آزمایش‌نشده».
