# CI/CD و محافظت در برابر آپدیت خراب

**تاریخ:** ۲۰۲۶-۱۱-۰۸ · **شاخه:** `arena/bd03e7a3-monshim`

> این سند وضعیت **واقعی** را می‌گوید، نه وضعیت مطلوب.
> هر جا چیزی پیاده نشده، صریح نوشته شده و دلیلش آمده.

## ۱. خلاصه — الان چه چیزی داریم؟

| لایه | وضعیت | اجرا شده؟ |
|---|---|---|
| CI (GitHub Actions) | ⚠️ **نوشته و تأیید شده، اما در مخزن نیست** | ✅ **۸ گام واقعاً اجرا شد** |
| CD (استقرار خودکار) | ❌ **وجود ندارد** | — |
| pre-commit hook | ✅ **نوشته و ۶ سناریو تست شد** | ✅ |
| Dependabot | ✅ **نوشته شده** | ❌ در مخزن نیست |
| Branch protection | ❌ **وجود ندارد** | — |

**صادقانه: از نظر «جلوگیری از آپدیت خراب»، فقط یک لایه واقعاً فعال است**
(quality gate داخل `lint`/`test`/`build` + pre-commit hook).
CI روی GitHub **فعال نیست** چون فایلش push نشده.

## ۲. CI — چه چیزی نوشته شد و چه چیزی تأیید شد

فایل: `.github/workflows/ci.yml` — دو job مستقل.

### گام‌ها و نتیجهٔ اجرای واقعی

**Backend** (pnpm 8.15.4، مطابق `packageManager`):

| گام | دستور | نتیجهٔ واقعی |
|---|---|---|
| نصب | `pnpm install --frozen-lockfile` | ✅ ۱۰ ثانیه |
| ۱ | `npx tsc --noEmit` | ✅ **exit 0** |
| ۲ | `pnpm run lint` (نه `lint:fix`) | ✅ **exit 0** |
| ۳ | `pnpm test -- --silent` | ✅ **۳۵۲ پاس + ۳ skip / ۳۵۵** |
| ۴ | `pnpm run build` | ✅ **exit 0** |
| ۵ | `test -f dist/src/main.js` | ✅ **exit 0** |

**Frontend** (pnpm 9، چون لاک‌فایل v9 است):

| گام | دستور | نتیجهٔ واقعی |
|---|---|---|
| نصب | `pnpm install --frozen-lockfile` | ✅ ۱۳.۸ ثانیه |
| ۱ | `npx tsc --noEmit` | ✅ **exit 0** |
| ۲ | `pnpm run lint` | ✅ **exit 0** (۲۰ warning) |
| ۳ | `pnpm test` | ✅ **۵۴ پاس، ۰ fail** |
| ۴ | `npm run build` | ✅ **exit 0** (۵۱ مسیر + inline CSS) |

> **نکتهٔ مهم:** این ۹ گام را **دستی و با همان دستورهای CI** اجرا کردم،
> نه با دستورهای دلخواه خودم. اولین اجرای CI روی GitHub هم همین را تأیید می‌کند.

### چرا دو نسخهٔ pnpm؟

```
back/pnpm-lock.yaml   → lockfileVersion: '6.0'  → pnpm 8 (packageManager: pnpm@8.15.4)
front/pnpm-lock.yaml  → lockfileVersion: '9.0'  → pnpm 9
```

pnpm 9 نمی‌تواند لاک‌فایل v6 را بخواند و برعکس. پس نمی‌شود یک نسخه برای هر دو داد.
CI این تفاوت را صریح منعکس می‌کند.

### ⛔ چرا CI در مخزن نیست

```
! [remote rejected] (refusing to allow a GitHub App to create or update
  workflow `.github/workflows/ci.yml` without `workflows` permission)
```

**دو مسیر را امتحان کردم و هر دو رد شد:**
1. `git push` ← خطای بالا
2. `gh api -X PUT .../contents/.github/workflows/ci.yml` ← `403 Resource not accessible by integration`

نکتهٔ عجیب: `gh api repos/.../` می‌گوید `admin: true`، ولی **مجوز `workflows`
یک scope جدای GitHub App است** و در این نشست وجود ندارد.

**راه‌حل برای شما (۳۰ ثانیه):**

```bash
# فایل آماده است، فقط کامیت و push کنید
cd <repo>
git add .github/
git commit -m "ci: add CI workflow and dependabot"
git push
```

یا در تنظیمات GitHub App دسترسی **Workflows** را فعال کنید.

## ۳. CD — وجود ندارد، و عمداً ساخته نشد

**هیچ pipeline استقرار خودکاری وجود ندارد.** دلیلش سه چیز است:

1. **اطلاعات سرور را نمی‌دانم.** میزبان، کاربر، مسیر پروژه، نام پروسه‌های PM2
   و روش احراز هویت — هیچ‌کدام در مخزن نیستند. ساختن CD با حدس، **بدترین**
   کاری است که می‌شود کرد (قانون: «هرگز اطلاعات production را حدس نزن»).
2. **استقرار فعلی دستی و با PM2 است.** CD بدون دانستن `cwd` و اکوسیستم PM2
   می‌تواند `.env` را جابه‌جا کند → زنجیرهٔ `cwd → .env → synchronize`
   که در `07-AUDITS.md` بند ج-۴ مستند شده.
3. **ریسک/فایده منفی است.** استقرار دستی ۲ دقیقه است و شما کنترل کامل دارید.
   CD خودکار روی پروژه‌ای که هنوز Audit Production کامل ندارد، ریسک را بالا می‌برد نه پایین.

**اگر روزی خواستید، حداقل‌ها این‌ها هستند:**
- یک `environment` در GitHub با approval دستی
- استقرار روی staging، نه مستقیم روی production
- `curl /api/health/ready` بعد از استقرار، با rollback خودکار در صورت شکست
- `pm2 reload` (نه `restart`) برای zero-downtime

## ۴. pre-commit hook — فعال و تست‌شده

فایل: `.githooks/pre-commit` (قابل commit و نسخه‌بندی)

**نصب یک‌باره روی هر clone:**
```bash
git config core.hooksPath .githooks
```

### چه چیزی را می‌گیرد

| # | بررسی | سرعت |
|---|---|---|
| ۱ | فایل `.env` در حال commit است | فوری |
| ۲ | کلید/توکن واقعی در کد | فوری |
| ۳ | `tsc --noEmit` بک‌اند (اگر تغییر کرده) | ~۱۵ ثانیه |
| ۴ | `tsc --noEmit` فرانت (اگر تغییر کرده) | ~۲۰ ثانیه |

**تست کامل و تست‌های PWA/Playwright عمداً این‌جا نیستند** — کند می‌شوند و
آدم‌ها را به `--no-verify` عادت می‌دهند. آن‌ها کار CI هستند.

### ۶ سناریو که واقعاً اجرا شد

| # | سناریو | نتیجهٔ انتظار | نتیجهٔ واقعی |
|---|---|---|---|
| ۱ | commit کردن `back/.env` | ⛔ بلاک | ✅ **بلاک شد** |
| ۲a | توکن بله در کد | ⛔ بلاک | ✅ **بلاک شد** |
| ۲b | API key با کوتیشن تک | ⛔ بلاک | ✅ **بلاک شد** |
| ۴a | کامنت معمولی حاوی `API_KEY` | ✅ رد شود | ✅ **رد شد** |
| ۴b | تغییر در `.env.example` | ✅ رد شود | ✅ **رد شد** |
| ۵ | خطای TypeScript | ⛔ بلاک | ✅ **بلاک شد** |

> **یک باگ واقعی که همین تست‌ها پیدا کردند:** نسخهٔ اول الگوی تشخیص کلید،
> توکن بله (`123456789:AAFake...`) را **نمی‌گرفت**، چون کاراکتر `:` در
> کلاس کاراکترها نبود. اگر تست نکرده بودم، یک hook معیوب تحویل می‌دادم که
> *به نظر می‌رسد کار می‌کند*. اصلاح شد و دوباره تست شد.

> **نکتهٔ صداقتی:** در تست اولم، `.env` را با `git add -f` اضافه کردم —
> یعنی هشدار «فایل .env» در حالت عادی حتی لازم نمی‌شد چون `.gitignore` جلویش را می‌گیرد.
> hook برای حالتی است که کسی `.gitignore` را خراب کند.

## ۵. Dependabot — نوشته شده، در مخزن نیست

فایل: `.github/dependabot.yml` (اعتبار YAML تأیید شد)

| گروه | دامنه | زمان‌بندی |
|---|---|---|
| `back-minor-patch` | patch + minor | هفتگی، دوشنبه |
| `front-minor-patch` | patch + minor | هفتگی، دوشنبه |
| GitHub Actions | اقدام‌های CI | ماهانه |

**major‌ها عمداً ignore شده‌اند** — ارتقای major باید دستی و با آزمون انجام شود.
این همان درسی است که فاز ۴ نشان داد: ۵۲ نسخهٔ وابستگی که خودکار عوض شوند
می‌توانند بی‌صدا چیزی را بشکنند.

## ۶. محافظت‌های دیگری که **وجود دارند** (از قبل یا از این شاخه)

| محافظ | چیست |
|---|---|
| `--frozen-lockfile` | نسخه‌ها در استقرار عوض نمی‌شوند |
| lockfile committed (هر دو پروژه) | بیلد قابل تکرار |
| `lint` ≠ `lint:fix` | lint هرگز فایل را بی‌صدا بازنویسی نمی‌کند |
| ۹۱۱ بردار همسانی | اگر منطق قیمت‌گذاری دو طرف از هم جدا شود، تست می‌شکند |
| ۳۵۵ تست بک‌اند | رفتار قفل شده |
| `sql/PRE-DEPLOY-CHECK.sql` | اسکیما قبل از استقرار بررسی می‌شود |
| `back/.env.example` | متغیرهای الزامی مستندند |
| hexcheck | `test -f dist/src/main.js` مطابقت build با `start:prod` |

## ۷. محافظت‌هایی که **وجود ندارند** — پیشنهاد، نیازمند تأیید

| # | پیشنهاد | فایده | هزینه | ریسک |
|---|---|---|---|---|
| ۱ | **Branch protection روی `main`** | کسی مستقیم push نکند؛ CI اجباری شود | ۱ دقیقه (تنظیمات GitHub) | ندارد |
| ۲ | **`engines` + `.nvmrc`** | نسخهٔ Node همه‌جا یکی شود | ۵ دقیقه، **تغییر در `package.json`** | پایین |
| ۳ | `npm audit` / `pnpm audit` در CI | آسیب‌پذیری شناخته‌شده | اضافه کردن ۱ گام | ممکن است فعلاً warning بدهد (`xlsx`) |
| ۴ | تست اسموک post-deploy | تأیید واقعی بعد از استقرار | متوسط | نیازمند دسترسی سرور |

**#۱ را قویاً توصیه می‌کنم** و هیچ کدنویسی لازم ندارد.
**#۲ را انجام ندادم** چون تغییر `package.json` است و قاعدهٔ شما «بدون تأیید فایل تغییر نکن» را نقض می‌کند.

## ۸. جمع‌بندی: «آپدیت خراب» چقدر مهار شده؟

**اگر آپدیتی چیزی را بشکند، کجا گرفته می‌شود؟**

```
نوشتن کد
   ├─ pre-commit hook ......... ✅ فعال (خطای TS، .env، کلید)
   ├─ push
   │    ├─ CI ................. ⛔ نوشته شده، ولی فعال نیست ← شکاف اصلی
   │    └─ (بدون branch protection) ← شکاف
   ├─ merge به main
   └─ استقرار دستی
        ├─ sql/PRE-DEPLOY-CHECK.sql ✅
        ├─ بکاپ + تست ری‌استور .... ✅ (دستی، در DEPLOY.md)
        └─ بدون تست اسموک خودکار ... شکاف
```

**پاسخ صادقانه:** لایهٔ محلی خوب است، لایهٔ GitHub **خاموش** است.
تا وقتی `.github/` کامیت نشود، **تنها محافظ واقعی، pre-commit hook و
انضباط شخصی است**. و hook هم فقط اگر `git config core.hooksPath .githooks`
روی هر clone اجرا شود کار می‌کند.

**کاری که همین حالا باید بکنید:** `git add .github/ && git commit && git push`
