# ساختار درخواستی شما — تحلیل و برنامهٔ اجرا

**تاریخ:** ۲۰۲۶-۱۱-۰۸
**وضعیت:** ⏸ **منتظر تأیید — هیچ فایلی جابه‌جا نشده**

> این سند پاسخ به درخواست بازآرایی به ساختار turbo/monorepo است.
> اول ریسک‌ها را با **اندازه‌گیری** می‌گویم، بعد برنامه. هیچ چیزی اجرا نشده.

---

## ۱. اول یک تناقض که باید بدانید

ساختاری که خواستید (`apps/`, `packages/`, `turbo.json`, `pnpm-workspace`) همان
**مونوریپو** است. در فاز ۴ این را با آزمایش واقعی بررسی کردیم و **رد شد**.
دلیلش این بود:

> `next build` در monorepo شکست می‌خورد · `pnpm@8.15.4` لاک‌فایل v9 را نمی‌خواند ·
> ۵۲ نسخهٔ وابستگی عوض می‌شد

**اما این «رد» به این معنا نیست که ساختار بد است.** معنايش این بود که
«الان و بدون آماده‌سازی، ریسکش از فایده‌اش بیشتر است». حالا که شما صریح
می‌خواهید، **قابل انجام است** — ولی با یک برنامهٔ مرحله‌ای، نه یک `git mv` بزرگ.

## ۲. اندازه‌گیری واقعی هزینه

### ۲-۱. حجم جابه‌جایی

| بخش | تعداد | توضیح |
|---|---|---|
| فایل TS/TSX بک‌اند | **۲۶۷** | `back/src` → `apps/api/src` |
| فایل فرانت | **~۴۰۰** | `front/*` → `apps/web/*` |
| ماژول‌های بک‌اند | **۲۲** | `barber`, `payment`, `booking`, ... → `modules/` |
| فایل‌های `common/` | **۴۸** | باید به ۹ زیرپوشه تقسیم شوند |
| import با الیاس `src/` (بک‌اند) | **۴۷۰** | همه باید بازنویسی شوند |
| import با الیاس `@/` (فرانت) | **۱٬۰۹۲** | همه باید بازنویسی شوند |
| فایل کانفیگ | **۱۹** | nest/swc/next/sentry/eslint/tsconfig |

**جمع: ۴۹ فایل جابه‌جا + ۱٬۵۶۲ import بازنویسی.**

### ۲-۲. 🔴 بلاکر واقعی: دو lockfile ناسازگار

این جدی‌ترین مسئله است و **آزمایش شد**:

```
back/pnpm-lock.yaml   → lockfileVersion: '6.0'  (pnpm 8)
front/pnpm-lock.yaml  → lockfileVersion: '9.0'  (pnpm 9)
```

در یک workspace، **فقط یک lockfile** در ریشه وجود دارد. آزمودم:

```
$ pnpm install   (workspace با هر دو package.json)
Done in 22.8s
$ head -1 pnpm-lock.yaml
lockfileVersion: '9.0'          ← v6 بی‌صدا به v9 ارتقا یافت
```

**نتیجهٔ اندازه‌گیری‌شده: ۵۳ پکیج نسخه عوض می‌کند**

```
api @nestjs/core      11.2.3 → 11.2.8
api express            5.2.1 →  5.3.0
api mysql2            3.24.4 → 3.24.6
api typeorm            1.1.1 →  1.1.2
api @sentry/nestjs    11.0.0 → 11.11.0
web @sentry/nextjs     11.4.0 → 11.11.0
... (۴۷ مورد دیگر)
```

هیچ‌کدام major نیستند، ولی **`mysql2`, `typeorm`, `express`** در میانشان
هستند — یعنی دقیقاً همان‌هایی که روی دیتابیس و API اثر دارند.

> **این هزینهٔ اجتناب‌ناپذیر ساختار است، نه ضعف اجرا.** راه فرار ندارد مگر
> اینکه `pnpm.overrides` را دقیقاً پین کنیم (که خودش کار بیشتری است).

### ۲-۳. 🔴 بلاکر دوم: `next build` در monorepo

در فاز ۴ اندازه گرفتیم: `next build` شکست می‌خورد چون Turbopack از مرز
`root` بیرون نمی‌رود.

**راه‌حل شناخته‌شده و آزمایش‌شده:**
```ts
// apps/web/next.config.ts
turbopack: { root: path.resolve(process.cwd(), '..', '..') }
```
با این، بیلد **۵۱ مسیر، exit 0** شد. ✅ آزمایش‌شده.

### ۲-۴. 🟡 ریسک: `uploads/`

`docker-compose.prod.yml` الان دارد:
```yaml
- ${UPLOADS_HOST_PATH:-./uploads}:/backend/uploads
```
`./uploads` نسبت به **محل فایل compose** است. اگر compose به `infra/` برود،
این مسیر عوض می‌شود → **فایل‌های آپلودی موجود «گم» می‌شوند** (فایل‌ها سر
جایشان می‌مانند، ولی سرویس جای دیگری نگاه می‌کند).

**راه‌حل:** در `infra/docker-compose.yml` مسیر را صریح کنید:
```yaml
- ${UPLOADS_HOST_PATH:-../apps/api/uploads}:/backend/uploads
```
**قبل از مهاجرت باید `UPLOADS_HOST_PATH` واقعی سرور را بدانید.**
این را از `pm2 env` / `docker inspect` می‌شود گرفت — **حدس نمی‌زنم.**

### ۲-۵. 🟡 ریسک: سه الیاس بدون خانه

در درخت هدف شما این‌ها جایی ندارند:

| الیاس | فایل‌ها | خانه در درخت شما؟ |
|---|---|---|
| `@/services` (۲۱۷ import) | `front/services/` | ❌ ندارد |
| `@/store` (۱۴) | `front/store/` | ❌ ندارد |
| `@/constants` (۲۴) | `front/constants/` | ❌ ندارد |
| `@/providers` (۱۰) | `front/providers/` | ❌ ندارد |

**پیشنهاد:** `store` → `lib/store/`، `constants` → `lib/constants/`،
`providers` → `app/providers/`، و `services/api` → `lib/api/`.
**ولی این یک تصمیم است، نه جزئیات — تأییدتان لازم است.**

### ۲-۶. 🟡 ریسک: `packages/contracts`

ساختار شما `packages/contracts` می‌خواهد — یعنی نوع‌های مشترک بک/فرانت.
**الان هیچ نوع مشترکی وجود ندارد** (هر طرف نوع خودش را دارد).
ساختن `contracts` یعنی **نوع‌های جدید نوشتن و هر دو طرف را به آن وصل کردن** —
این «بازآرایی» نیست، **توسعهٔ قابلیت جدید** است و ریسک تغییر رفتار دارد.

**پیشنهاد من:** اول ساختار را بسازید، `contracts` را در فاز جدا و با
تأیید جدا انجام دهید. `shared/` فعلی (بردارهای هم‌سانی) می‌تواند به
`packages/contracts/vectors/` برود — آن بی‌خطر است.

## ۳. برنامهٔ پیشنهادی: ۶ فاز مستقل

> هر فاز یک commit و **قابل برگشت** است. بعد از هر فاز: `tsc` + `eslint` + تست.

| کار | نتیجه |
|---|---|

## ۴. تأثیر روی Production — این را باید بدانید

| مورد | تغییر می‌کند؟ | ریسک |
|---|---|---|
| پورت‌ها | ❌ | ۰ |
| API routes | ❌ | ۰ |
| اسکیمای DB | ❌ | ۰ |
| `uploads/` | ⚠️ **مسیر host** | **باید تأیید شود** |
| PM2 `cwd` | ⚠️ **عوض می‌شود** | متوسط |
| Docker build context | ⚠️ `back/` → `apps/api/` | متوسط |
| Nginx | ❌ | ۰ |
| `.env` | ❌ محتوا | ۰ (ولی مسیرش) |

### 🔴 خطری که باید جدی بگیرید

`ConfigModule` هیچ `envFilePath` ندارد و `.env` را از `process.cwd()` می‌خواند.
اگر ساختار عوض شود و `cwd` PM2 عوض شود:

```
cwd غلط → .env لود نمی‌شود → NODE_ENV=undefined
→ synchronize: undefined !== 'production' → true
→ TypeORM اسکیما را هم‌تراز می‌کند → خطر روی production
```

**این زنجیره الان هم وجود دارد** (مستند شده در `07-AUDITS.md`)، ولی
جابه‌جایی ساختار **احتمال رخدادش را بالا می‌برد**.

**پیشنهاد اجباری:** قبل از فاز M1، این گارد اضافه شود:
```ts
// apps/api/src/common/config/typeorm.config.ts
if (!process.env.NODE_ENV) {
  throw new Error('NODE_ENV تعریف نشده — بوت متوقف شد تا از synchronize ناخواسته جلوگیری شود');
}
```
این **تغییر رفتار** است، پس منتظر تأیید شماست. ولی بدونش، فاز M1 خطرناک است.
