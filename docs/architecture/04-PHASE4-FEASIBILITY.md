# فاز ۴ (Monorepo) — گزارش امکان‌سنجی

**نتیجهٔ کوتاه: انجامش می‌دهم، اما باید بدانید چه چیزی قربانی می‌شود.**

---

## ۱. مشکلی که پیدا کردم

شما گفتید: «ساختار تغییر کند، ولی محتویات فایل‌ها آسیب نبیند».

هنگام اجرا متوجه شدم `pnpm workspace` **دقیقاً همان چیزی را می‌شکند که شما نگرانش بودید** — نه در فایل‌های سورس، بلکه در **وابستگی‌های نصب‌شده**.

### آزمایش واقعی

یک کپی موقت ساختم، `pnpm-workspace.yaml` گذاشتم و لاک‌فایل واحد تولید کردم:

```yaml
packages:
  - back
  - front
```

نتیجه، مقایسه با نسخه‌های **نصب‌شدهٔ فعلی**:

| پروژه | وابستگی مستقیم | نسخه تغییر کرد |
|---|---|---|
| **back** | ۵۸ | **۲۳** |
| **front** | ۵۷ | **۳۰** |

نمونه‌ها:

```
@nestjs/core        11.2.3 → 11.2.8
@nestjs/throttler    6.5.0 → 6.7.1
@sentry/nestjs      11.0.0 → 11.11.0
express              5.2.1 → 5.3.0
mysql2              3.24.4 → 3.24.6
@tanstack/react-query 5.104.1 → 5.107.1
@tiptap/*           3.32.2 → 3.33.0   (۱۲ پکیج)
```

**هیچ‌کدام major نیستند** (SemVer سازگار)، اما:

> ❗️ **این دقیقاً «تغییر محتویات» است.** کد شما عوض نمی‌شود، اما وابستگی‌هایی که اجرا می‌شوند عوض می‌شوند. `mysql2` (درایور دیتابیس)، `express` (وب‌سرور) و `typeorm` همه تغییر می‌کنند.

### چرا اجتناب‌ناپذیر است؟

`back/pnpm-lock.yaml` نسخهٔ **v6** و `front/pnpm-lock.yaml` نسخهٔ **v9** است.
یک workspace **یک** لاک‌فایل دارد و باید v9 باشد.
pnpm نمی‌تواند دو لاک‌فایل قدیمی را «ادغام» کند؛ **همه را از نو resolve می‌کند.**

تنها راه جلوگیری: قفل کردن دستی ۱۱۵ وابستگی به نسخهٔ دقیق (حذف `^`). این هم خودش تغییر بزرگی است و **به‌روزرسانی آینده را متوقف می‌کند**.

## ۲. راه‌حل‌های ممکن

### گزینه الف — Monorepo واقعی (کاری که Ravand می‌کند)

```yaml
# pnpm-workspace.yaml — نام پوشه‌ها را عوض نمی‌کنیم (PM2 سالم می‌ماند)
packages:
  - back
  - front
  - packages/*
```

| + مزیت | − هزینه |
|---|---|
| یک لاک‌فایل، نصب واحد | **۵۳ پکیج نسخه عوض می‌کند** |
| کش مشترک (نصب سریع‌تر) | لاک‌فایل ۵۴۰ KB جدید |
| `packages/contracts` ممکن می‌شود | باید کل تست‌ها + Build دوباره تأیید شود |
| اسکریپت‌های واحد در ریشه | ریسک `nest build` با symlink (نیازمند `node-linker=hoisted`) |

**ریسک اصلی:** `node_modules` ساختار کاملاً متفاوتی پیدا می‌کند. Monshim امروز **۳۲۵ تست بک‌اند + ۵۴ تست فرانت** دارد که همه با ساختار فعلی پاس می‌شوند. بعد از مهاجرت، اگر چیزی بشکند، ریشه‌یابی سخت است — چون هم ساختار و هم نسخه‌ها هم‌زمان عوض شده‌اند.

### گزینه ب — Workspace بدون نصب مجدد (ترفند)

`pnpm-workspace.yaml` اضافه شود **اما** `node_modules`های موجود دست نخورند.

| + | − |
|---|---|
| صفر تغییر در وابستگی‌های اجرایی | شکننده: هر `pnpm install` بعدی همه چیز را عوض می‌کند |
| تست‌ها بلافاصله معتبر می‌مانند | یک لاک‌فایل واحد نداریم → همان مشکلی که می‌خواستیم حل کنیم، حل نمی‌شود |

**حکم من: این گزینه را توصیه نمی‌کنم.** یک راه‌حل نیمه‌کاره که مشکل اصلی (تکرارپذیری Deploy) را حل نمی‌کند و توهم امنیت می‌دهد.

### گزینه ج — Monorepo + قفل نسخه‌ها

همان گزینه الف، اما قبل از مهاجرت همهٔ `^`ها به نسخهٔ دقیق تبدیل شوند تا هیچ نسخه‌ای عوض نشود.

| + | − |
|---|---|
| **صفر تغییر در وابستگی‌ها** | ۱۱۵ خط تغییر در `package.json` |
| لاک‌فایل واحد واقعی | **به‌روزرسانی امنیتی خودکار از بین می‌رود** (بدون Dependabot) |
| Deploy قابل تکرار | کار بیشتری لازم است |

### گزینه د — Monorepo را انجام ندهیم

| + | − |
|---|---|
| صفر ریسک | یک لاک‌فایل واحد نداریم؛ ساختار شبیه Ravand نمی‌شود |
| همهٔ سودهای فاز ۱–۳ حفظ می‌شود | `packages/contracts` ممکن نیست |

## ۳. آنچه **بدون** monorepo هم به دست آمد

مهم است بدانید چه چیزی را از دست نمی‌دهید:

| هدف | وضعیت فعلی |
|---|---|
| حذف کد مرده | ✅ فاز ۱ |
| `tsc` و `eslint` سبز | ✅ فاز ۲ (واقعاً ۰ خطا) |
| **منطق پول یکتا/قفل‌شده** | ✅ فاز ۳ — ۸۲۸ بردار |
| **منطق کد ملی و ارقام قفل‌شده** | ✅ فاز ۳ — ۸۳ بردار |
| حذف تکرار درون‌پروژه‌ای | ✅ فاز ۳ |
| تست‌های خاموش احیا | ✅ ۵۶ تست |

بنابراین **فاز ۴ برای رسیدن به سودهای اصلی لازم نیست.** آنچه monorepo اضافه می‌کند:
- یک لاک‌فایل (تکرارپذیری Deploy)
- `packages/contracts` (حذف کامل دوگانگی، نه فقط قفل آن)
