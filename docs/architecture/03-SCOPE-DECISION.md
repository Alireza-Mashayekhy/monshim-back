## ۱. «ساختار تغییر کنه ولی محتویات فایل‌ها تغییر نکنه» — آیا ممکن است؟

**بله. و حتی امن‌تر از آنچه فکر می‌کردم.**

من با شواهد بررسی کردم که اگر پوشه‌ها را جابه‌جا کنیم، آیا مجبور می‌شویم داخل فایل‌ها را دست بزنیم یا نه:

| بررسی | نتیجه | معنا |
|---|---|---|
| Import از یک پروژه به پروژهٔ دیگر | **۰ مورد** | back و front هیچ کدی از هم نمی‌گیرند |
| Import نسبی که از ریشهٔ اپ بیرون بزند | **۰ مورد** | هر فایل فقط داخل اپ خودش است |
| مسیر مطلق سرور در کد/کانفیگ | **۰ مورد** | `/var/www` و امثالش وجود ندارد |
| `baseUrl` بک‌اند | `"./"` | نسبت به محل خودِ `tsconfig` است → با جابه‌جایی سالم می‌ماند |
| `paths` فرانت | `"@/*": ["./*"]` | نسبت به محل خودِ `tsconfig` است → سالم می‌ماند |
| خروجی Build بک‌اند | `require("src/…")` = **۰** | TypeScript مسیرها را خودش نسبی می‌کند |

**نتیجهٔ فنی:** جابه‌جایی پوشه یک عملیات `git mv` است. **صفر خط داخل فایل‌ها عوض نمی‌شود** و کد همان کد قبلی است، بایت‌به‌بایت.

**اما** — این را باید صریح بگویم، چون همان چیزی است که منظورم از «scope» بود:

> 🔴 **جابه‌جایی ساختار، به‌تنهایی، هیچ سودی برای پروژه ندارد.**
> هیچ باگ را رفع نمی‌کند، هیچ چیز را سریع‌تر نمی‌کند. فقط شکل پوشه‌ها شبیه Ravand می‌شود.
>
> سودهای واقعی از چیزهای دیگری می‌آید که **محتوا** را تغییر می‌دهند:
> • حذف کد مرده (فاز ۱)
> • یکتا کردن منطق قیمت‌گذاری که الان **دو نسخه** دارد (فاز ۳) ← این خطر مالی واقعی است
> • health endpoint، اعتبارسنجی env، خاموشی تمیز (فاز ۵)

پس سؤال واقعی این نیست «ساختار یا محتوا»، بلکه این است:
**چقدر اجازه دارم داخل فایل‌ها دست بزنم؟** پاسخ این در بخش ۳ آمده.

## ۲. 🚨 کشف مهم: PM2 — جابه‌جایی `front/` می‌تواند Production را بخواباند

شما گفتید فرانت با **PM2** اجرا می‌شود. این یک واقعیت تعیین‌کننده است که باید بدانید:

- در مخزن **هیچ `ecosystem.config.js` وجود ندارد** (بررسی شد). یعنی تنظیم PM2 **فقط روی سرور** است.
- آن تنظیم شامل `cwd` و مسیر اسکریپت است، مثلاً چیزی شبیه `/var/www/monshim/front`.
- اگر پوشهٔ `front/` را به `apps/web/` تغییر نام دهیم، **در اولین `pm2 restart` سرویس بالا نمی‌آید.**

این دقیقاً همان چیزی است که شما گفتید نباید اتفاق بیفتد: «سرویس‌ها بعد از restart سرور از کار نیفتند».

### ✅ راه‌حل: نام پوشه‌ها را عوض نکنیم

**pnpm workspace به پوشه‌ای به نام `apps/` نیاز ندارد.** می‌توانیم این را بنویسیم:

```yaml
# pnpm-workspace.yaml
packages:
  - back
  - front
  - packages/*
```

با این کار **همهٔ سودهای monorepo** را می‌گیریم (یک لاک‌فایل، پکیج مشترک، اسکریپت‌های واحد، کش مشترک) **بدون اینکه یک مسیر عوض شود.**

| چه چیزی سالم می‌ماند | چرا |
|---|---|
| تنظیم PM2 روی سرور | مسیر `front/` دست‌نخورده |
| `docker-compose` و `build: context: .` | پوشهٔ `back/` سر جایش |
| Nginx reverse proxy | پورت ۳۰۰۰ و ۳۰۰۲ دست‌نخورده |
| `.env` ها | جابه‌جا نمی‌شوند |
| `uploads/` | مسیر فیزیکی همان است |
| `back/dist/src/main` | همان مسیر، همان CMD |

> این را «**گزینهٔ امن**» می‌نامم. سود کامل، ریسک تقریباً صفر.
> اگر بعداً خواستید نام‌ها را به `apps/*` ببرید، آن یک کار جداگانه در یک پنجرهٔ نگهداری است — نه بخشی از این پروژه.

## ۳. چهار سطح «دست زدن به محتوا» — کدام را اجازه می‌دهید؟

شما به سطح ۱ «بله» گفتید. بقیه را لطفاً مشخص کنید:

### سطح ۰ — فقط ساختار (صفر خط تغییر در فایل‌های کد)

`git mv` + `pnpm-workspace.yaml` + ادغام لاک‌فایل + ادغام `.gitignore` + `tsconfig.base.json`.

- ✅ هیچ فایل `.ts`/`.tsx` باز نمی‌شود
- ⚠️ **استثنا:** دو فایل **باید** تغییر کنند، چون بدون آن‌ها Build می‌شکند:
  1. `back/dockerfile` → مسیر `COPY` لاک‌فایل (چون لاک‌فایل به ریشه منتقل می‌شود)
  2. `package.json` ریشه → اسکریپت‌ها و وابستگی‌ها
- 🔴 **خطر پنهانی که پیدا کردم:** `.gitignore` ها مسیرمحورند. الان `back/.gitignore` خط `uploads/` دارد. اگر آن را در `.gitignore` ریشه ادغام کنیم و قاعده را دقیق ننویسیم، **فایل‌های آپلودی Production به گیت اضافه می‌شوند.** (جالب اینکه همین حالا ۶ فایل webp داخل `back/uploads/` در گیت track شده‌اند — یعنی یک‌بار این اتفاق افتاده.) این را با قاعدهٔ صریح `apps/…/uploads/` یا `back/uploads/` حل می‌کنم و **قبل از commit با `git status` نشانتان می‌دهم.**

### سطح ۱ — اصلاحات مکانیکی (✅ تأیید شد)

مرتب‌سازی import و حذف import بی‌استفاده برای سبز شدن ESLint. تغییرات تک‌خطی، صفر تغییر رفتار.

### سطح ۲ — یکتا کردن کد تکراری

توابعی که **دو نسخه** دارند به `packages/contracts` منتقل می‌شوند و نسخهٔ دوم حذف می‌شود. ۴ فایل importشان یکی عوض می‌شود.

**تعهد من:** یک تست تفاضلی می‌نویسم که ۱۰۰۰ ورودی تصادفی به **نسخهٔ قدیم و نسخهٔ جدید** بدهد و خروجی را مقایسه کند. تا وقتی خروجی‌ها بایت‌به‌بایت یکسان نباشند، کد قدیمی حذف نمی‌شود.

### سطح ۳ — افزودنی

فایل‌های **جدید** (`health`، `env.ts`، `setup-app.ts`). فایل‌های موجود حداکثر ۳ خط اضافه می‌گیرند (`main.ts`).

### 🚫 سطح ۴ — دیتابیس: **از این پروژه بیرون است**

بدون بکاپ و پنجرهٔ نگهداری، به دیتابیس دست نمی‌زنم. اگر بخواهید، کار کاملاً جدا و بعد از پایان بقیه.

## ۴. `extractBaseDepositToken` — «این برای چه کاریه؟ کدوم بهتره؟»

### این تابع چه کار می‌کند؟
توکن لینک بیعانه را «تمیز» می‌کند. بک‌اند توکن را این‌طور می‌سازد:

```
randomBytes(12).toString('hex')  →  ۲۴ کاراکتر هگز
```

و اگر یک نوبت چند خدمت داشته باشد، به خدمت دوم `:1` اضافه می‌شود: `a1b2…ef:1`.

تابع `extractBaseDepositToken` آن `:1` را می‌بُرد تا لینک کپی‌شده برای کل نوبت کار کند.

### تفاوت دو نسخه — فقط **یک خط**

```
نسخهٔ فرانت :  طول بین ۸ و ۶۴ باشد           → قبول
نسخهٔ بک‌اند:  همان + /^[a-zA-Z0-9-]+$/ هم باشد → قبول
```

### کدام بهتر است؟ **نسخهٔ بک‌اند.**

| دلیل | توضیح |
|---|---|
| قوی‌تر است | کاراکترهای غیرمجاز را رد می‌کند |
| مرجع است | بک‌اند صاحب داده است؛ فرانت فقط نمایش می‌دهد |
| تست دارد | `deposit-amount.spec.ts:159-173` این رفتار را قفل کرده |
| **در عمل یکسان‌اند** | توکن همیشه خروجی `randomBytes().hex` است؛ کاراکتر غیرمجاز **هرگز** تولید نمی‌شود |

**تنها تفاوت رفتاری ممکن در فرانت:** اگر توکنی خراب باشد، به‌جای اینکه **لینک شکسته نشان داده شود**، لینک **مخفی** می‌شود. این بهتر است، نه بدتر.

> ✅ **پیشنهاد من:** نسخهٔ بک‌اند مبنا باشد. اما چون این کد **مالی/بیعانه** است، تا وقتی شما تأیید نکنید آن را لمس نمی‌کنم.
